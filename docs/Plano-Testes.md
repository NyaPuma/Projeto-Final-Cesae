# 🧪 Test Plan: Integrated Maintenance Management System

**Objective:** Validate the integrity of data flows (MySQL), security restrictions (RBAC), AI engine logic (SAD) and real-time event reactivity. This document serves as a guide for the team's *Quality Assurance* (QA) phase for the ACCEPT Review.

---

## 1. Authentication and Role Testing Matrix (RBAC)
*Objective: Ensure absolute isolation of routes and permissions according to the authenticated role.*

* **CT01: Security Lock Validation (Operator)**
    * **Scenario:** An authenticated operator (operative) tries to manually access Backoffice administrative routes via URL or Postman, such as `/api/admin/audits` or profile creation.
    * **Expected Result:** The Middleware intercepts the request, denies access immediately and returns the HTTP `403 Forbidden` code, protecting identity and audit data.
* **CT02: Password Persistence and Change**
    * **Scenario:** The user requests to change their credentials in the profile.
    * **Expected Result:** The controller processes the new string, applies the *hashing* algorithm (Bcrypt) and successfully updates the immutable field in MySQL. The old session token is invalidated.

---

## 2. Ticket Workflow Testing Matrix (Core Business)
*Objective: Ensure that the incident life cycle follows strict business rules without logical failures.*

* **CT03: Status Transition and Timestamp Capture**
    * **Scenario:** The Technician clicks the "Start Repair" button on the global panel.
    * **Expected Result:** The ticket status transitions from `Aberto` to `Em Curso`, the technician's ID is linked to the `assigned_to` field in MySQL, and the `in_progress_at` column captures the exact timestamp generated by the server (`NOW()`) for timing the intervention.
* **CT04: Conditional Cancellation Lock**
    * **Scenario:** The operator tries to cancel a ticket they submitted, but the ticket is already under technical handling (Status: `Em Curso`).
    * **Expected Result:** The interface omits the cancel button. If the user tries to force the request via a direct API call, the Back-End blocks the operation (HTTP 403), preserving the integrity of the life cycle.
* **CT05: Mandatory Closure with Cost Data**
    * **Scenario:** The Technician tries to submit the closure of a ticket (change to `Fechado`) leaving work minutes, resolution note or internal material costs blank.
    * **Expected Result:** The Laravel validation *Form Request* fails, prevents the database write (rejecting the UPDATE) and returns friendly JSON errors (HTTP 422) listing the mandatory operational fields.

---

## 3. Reactivity and Artificial Intelligence Testing Matrix (SAD)
*Objective: Validate the intelligent data layer, integrations and asynchronous broadcasts.*

* **CT06: Reactive Broadcasting via WebSockets (Laravel Echo)**
    * **Scenario:** A technician completes the physical closure of a work order at the factory and submits the closing data.
    * **Expected Result:** The `TicketStatusUpdatedBroadcast` event is fired synchronously. The Administrator's interface (Maintenance Director) captures the channel push and reactively updates the KPI charts (`Chart.js`) in real time, without needing to refresh the page.
* **CT07: Assisted Dispatch and AI Engine Persistence**
    * **Scenario:** The Administrator opens the details of a fault and clicks to allocate the professional suggested by the `AIService`.
    * **Expected Result:** The controller invokes the OpenAI API via the `gpt-4o-mini` model, processes the description through NLP and returns a structured JSON response containing the ideal `tecnico_id` and the justification. Upon validating, the Administrator submits the route `PATCH /admin/tickets/{id}/atribuir` and definitively records the assisted decision in MySQL.

---

## 4. Data Integrity Testing Matrix (DBA)
*Objective: Ensure physical consistency and prevent orphaned data or referential inconsistencies in MySQL.*

* **CT08: Deletion Restriction and Foreign Keys**
    * **Scenario:** The Administrator tries to logically or physically delete a `Sala` (room) or a system user that has active links to equipment or workflow histories.
    * **Expected Result:** The MySQL database protects orphaned data following the restriction rules of the migrations (`nullOnDelete()` for optional relationships or integrity blocking). Laravel catches the SQL exception and prevents any break in the structural tree of system tables.
